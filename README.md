# 3D Elmagd — نسخة GitHub Pages + Supabase

نسخة من موقع **3D Elmagd** بنفس التصميم حرفيًا، لكنها تعمل بلا سيرفر:
الواجهة ملفات ثابتة على **GitHub Pages**، وكل ما كان يفعله الـ backend
انتقل إلى **Supabase** (قاعدة بيانات + تخزين صور + تسجيل دخول).

> النسخة الأصلية (Next.js + Laravel + PostgreSQL) محفوظة كما هي في مجلد
> `elmagd 2` لتشغيلها على VPS ودومين لاحقًا. هذه النسخة مستقلة عنها تمامًا.

---

## ما الذي تغيّر عن النسخة الأصلية؟

| | النسخة الأصلية | هذه النسخة |
| --- | --- | --- |
| التصميم والصفحات | — | **بلا أي تغيير** |
| الاستضافة | سيرفر Next.js | GitHub Pages (ملفات ثابتة) |
| الـ backend | Laravel + Sanctum | لا يوجد — المتصفح يتكلم مع Supabase |
| القاعدة | PostgreSQL على Docker/VPS | PostgreSQL على Supabase |
| صور الأعمال | تخزين Laravel | Supabase Storage |
| الدخول | كلمة سر + كوكي موقّعة على السيرفر | Supabase Auth |
| حماية اللوحة | `proxy.ts` + Server Actions | **Row Level Security داخل Postgres** |
| حساب سعر الطلب | `QuoteCalculator.php` | دالة `calculate_quote` داخل القاعدة |

ملفات التصميم لم تُمس: `components/views` و`components/ui` و`components/three`
و`styles/globals.css` مطابقة حرفيًا للنسخة الأصلية.

## التشغيل المحلي

```bash
npm install
cp apps/web/.env.example apps/web/.env.local   # ضع فيه مفاتيح Supabase
npm run dev                                    # http://localhost:3000
```

بدون مفاتيح Supabase يعمل الموقع على محتوى البداية داخل المتصفح،
فيمكن تطوير الواجهة وحدها — وتُفتح لوحة التحكم في وضع التطوير فقط للمعاينة.

| الأمر (من الجذر) | الوظيفة |
| --- | --- |
| `npm run dev` | خادم التطوير |
| `npm run build` | بناء الموقع الثابت في `apps/web/out` |
| `npm run preview` | تقديم الملفات المبنية محليًا |
| `npm run lint` | ESLint |
| `npm run typecheck` | فحص الأنواع |
| `npm run test` | اختبارات Vitest |
| `npm run seed:sql` | إعادة توليد `supabase/seed.sql` من محتوى البداية |

**النشر:** راجع [`docs/deployment.md`](docs/deployment.md) — ثماني خطوات من الصفر.

> قبل أول رفع: انقل `docs/deploy-workflow.yml` إلى `.github/workflows/deploy.yml`
> (التفاصيل في [`docs/README-workflow.md`](docs/README-workflow.md)).

### مبدأ التنظيم

- **`lib/domain`** منطق أعمال خالص بلا React وبلا DOM: التسعير، قراءة STL، بناء روابط واتساب.
- **`lib/data`** طبقة الوصول للبيانات خلف واجهة `ContentRepository` واحدة. الواجهة لا تعرف من أين يأتي المحتوى.
- **`lib/supabase`** كل ما يخص Supabase في مكان واحد: العميل وترجمة الأعمدة.
- **`components/ui`** عناصر بلا منطق أعمال. **`components/views`** تركيب الصفحات فقط.

## الأمان — وأين يقع الفرق الحقيقي

على استضافة ثابتة لا يوجد سيرفر يوقف الطلب قبل وصوله، لذلك **الحماية كلها
انتقلت إلى داخل قاعدة البيانات**، وهذا أقوى لا أضعف: القواعد تُنفَّذ في Postgres
نفسه ولا يمكن الالتفاف عليها من المتصفح مهما فعل أحد.

**ما يحرسه `supabase/schema.sql`:**

- المحتوى (خدمات، أعمال، خامات، أسئلة، إعدادات): **القراءة للجميع، والكتابة للمالك وحده.**
- الطلبات: **لا يقرأها ولا يعدّلها إلا المالك.** لا توجد سياسة `insert` أصلًا،
  فالإدراج يمر حصرًا عبر دالة `submit_order` التي تتحقق من المدخلات
  **وتعيد حساب السعر من أسعار الخامات في القاعدة** — أي سعر يرسله المتصفح يُتجاهل.
- الصور: القراءة عامة، والرفع والحذف للمالك وحده.
- «المالك» = الجلسة التي بريدها هو بريد `owner_email()` وحالتها `authenticated`.
  حساب آخر مسجَّل دخوله لا يساوي شيئًا: لا يقرأ طلبًا ولا يكتب حرفًا.

**ماذا يعني ذلك عمليًا؟** أي شخص يستطيع فتح `/admin` أو نداء الـ API من كونسول
متصفحه — وسيجد صفحة فارغة وطلبات مرفوضة. هذا سلوك مُختبَر لا افتراض:
`supabase/tests/rls-test.sql` يشغّل هذه المحاولات فعليًا على PostgreSQL ويتأكد من رفضها.

**زر «لوحة التحكم»** لا يوجد في HTML أي صفحة تصل إلى أي زائر؛ يظهر في متصفح المالك
فقط بعد أن يؤكّد Supabase جلسته.

**إنشاء الحساب اختياري تمامًا للعميل:** الزائر بلا حساب يستخدم الموقع والمعاين
والطلب عبر واتساب بالكامل.

> **تنبيه واحد مهم:** لا تضع `service_role key` في هذا المشروع إطلاقًا.
> هو المفتاح الوحيد الذي يتجاوز كل ما سبق، ووضعه في موقع ثابت يعني تسليم القاعدة للجميع.

## المحتوى ولوحة التحكم

كل نص وسعر وصورة في الموقع يأتي من `SiteContent` ويُحرَّر من `/admin`:

| التبويب | ما يتحكم فيه |
| --- | --- |
| الطلبات | سجل الطلبات القادمة من الموقع وتغيير حالة كل طلب |
| الهوية والألوان | الاسم، اللوجو، اللون الأساسي ولون التمييز، الوضع الافتراضي |
| نصوص الموقع | عنوان الصفحة الرئيسية، الأزرار، شريط الأرقام، قسم الماكينة |
| الصفحات والقائمة | إظهار/إخفاء أي صفحة وتغيير اسمها في القائمة |
| الخدمات · الأعمال · الخامات · الأسئلة | إضافة وتحرير وترتيب وحذف |
| بيانات التواصل | رقم الواتساب (وجهة كل الطلبات)، العنوان، السوشيال، العملة |
| النسخ والاستعادة | تصدير/استيراد JSON وإعادة الضبط |

التعديل يُحفظ تلقائيًا بعد توقف الكتابة بلحظة، ويظهر في الموقع فورًا.

## الطلبات عبر واتساب

لا يوجد دفع أونلاين. زر الطلب في المعاين ونموذج التواصل يفتحان `wa.me` برسالة مرتّبة
(الملف، الخامة، الكمية، الوزن، الزمن، السعر التقديري)، **ويُسجَّل الطلب في قاعدة
Supabase بالتوازي** فيظهر في تبويب «الطلبات» حتى لو لم يكمل العميل الإرسال.
الأرقام المحلية تُحوَّل تلقائيًا للصيغة الدولية.

## نموذج التسعير

```
الوزن   = الحجم × الكثافة × (0.26 + 0.0074 × التعبئة) × (1 + الدعامات/260)
الزمن   = (الوزن ÷ 17) × (0.20 ÷ ارتفاع الطبقة) + 0.4 ساعة تسخين
السعر   = رسوم التجهيز + (الوزن × سعر الجرام + الزمن × سعر الساعة) × الكمية
```

رسوم التجهيز تُحتسب **مرة واحدة لكل طلب** لا لكل قطعة، فالكميات تعطي سعر وحدة أقل.

النموذج مكتوب مرتين عمدًا: `apps/web/src/lib/domain/pricing.ts` ليعرض المتصفح السعر
فورًا، ودالة `calculate_quote` في `supabase/schema.sql` لتحسب القاعدة السعر المخزَّن
مع الطلب — فلا يمكن تزويره من أدوات المطوّر. التطابق محروس باختبار
`pricing.parity.test.ts` الذي يقارن ثوابت النموذج بملف SQL حرفًا بحرف.

## الخطوة القادمة (اختيارية): دخول العملاء بجوجل

البنية جاهزة لها: يكفي تفعيل موفّر Google في Supabase وإضافة زر دخول في الموقع.
الحساب يبقى **اختياريًا تمامًا** — يضيف مزايا (سجل الطلبات) ولا يمنع شيئًا عمّن لا يملكه.
وعمود `orders.customer_id` موجود بالفعل ويُملأ تلقائيًا عند وجود جلسة.
